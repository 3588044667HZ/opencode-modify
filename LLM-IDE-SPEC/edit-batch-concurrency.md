# `edit-batch-concurrency.md`

## 目标

为 `edit_batch` 内建文件级并发写保护。保证多 agent 并行时，同一文件的编辑串行等价（linearizable）——不会出现“两个写者基于同一版本，后写覆盖先写”的静默覆盖。

这是 `edit_batch` 的增强，不是新原语。方法签名不变，行为扩展。

## 核心机制

**文件级互斥锁 + 版本戳校验 = 串行等价。**

`edit_batch` 的执行路径变为：

```
1. 规范化文件路径（绝对路径，统一分隔符）
2. 获取该文件的互斥锁（FIFO 等待，超时 30s）
3. 校验 baseVersion 与当前版本
4. 校验路径保护、内容纯度
5. 内存中应用所有 changes
6. 原子写入（tmp + fsync + rename）
7. 更新版本戳、触发索引/诊断失效
8. 释放锁
```

**锁 + 校验缺一不可**：

- 只有锁，没有校验 → 两个写者串行执行，但后写者基于旧版构造 changes，静默写错
- 只有校验，没有锁 → 校验和写入之间有窗口期，两个写者可能都通过校验，后写覆盖先写

两者合起来，才是串行等价。

## 锁的粒度与位置

**粒度：文件级。** 每个文件一个互斥锁。不同文件不互斥，可以并行。

**位置：IntelliJ 守护进程内。** 写路径在 IntelliJ 侧，锁也在 IntelliJ 侧。OC 侧不发锁请求，只发 `edit_batch`；守护进程内部处理锁。

**进程内锁。** 单项目单守护进程，锁不需要跨进程。如果将来多项目多守护，各自持有各自项目的锁，天然隔离。

**读不加锁。** `read_view`、`blast_radius`、`project_map` 都是只读，不获取写锁。它们可能读到旧版本，但返回的版本戳标注了这一点。

## 版本戳校验的时机

**校验必须在锁内。** 这是关键：

```
获得锁
  ↓
校验 baseVersion == 当前版本   ← 锁内校验
  ↓
应用 + 写入
  ↓
释放锁
```

如果校验在锁外，窗口期就存在。锁内校验保证：校验和写入之间没有其他写者介入。

## 等待与超时

**FIFO 等待。** 多个 `edit_batch` 等待同一文件时，按到达顺序获取锁，避免饥饿。

**超时：默认 30 秒，可配置。**

- 超时 → 返回 `LOCK_TIMEOUT`
- 模型可以重试，或先读最新版本再决定

**为什么是 30 秒：** `edit_batch` 本身应该很快（内存应用 + 原子写，通常 < 100ms）。30 秒超时意味着“如果等这么久还没拿到，说明有异常”——可能是某个写者卡住，可能是死锁（虽然单文件不会），可能是系统负载过高。

## 错误码

新增：

| 码 | 名称 | 触发 |
|---|---|---|
| -32017 | `LOCK_TIMEOUT` | 等待文件锁超时 |

已有错误码不变（`-32010` 到 `-32016`）。

`LOCK_TIMEOUT` 的返回：

```json
{
  "applied": false,
  "error": {
    "code": -32017,
    "message": "LOCK_TIMEOUT",
    "detail": {
      "file": "engine.ts",
      "waited_ms": 30000
    },
    "hint": "文件正被其他写者占用。可稍后重试，或先 read_view 获取最新版本"
  }
}
```

## 冲突场景

**场景一：两个 agent 基于同一版本改同一文件。**

```
Agent A: read engine.ts → v1
Agent B: read engine.ts → v1

A: edit_batch(engine.ts, changes_a, baseVersion=v1)
  → 获得锁 → 校验 v1==v1 → 写入 → 版本变 v2 → 释放锁

B: edit_batch(engine.ts, changes_b, baseVersion=v1)
  → 等待锁 → 获得锁 → 校验 v1≠v2 → VERSION_MISMATCH
```

B 被拒绝，返回最新内容（v2）。B 可以基于 v2 重新构造 changes。

**场景二：两个 agent 改不同文件。**

无冲突。各自获得各自文件的锁，并行执行。

**场景三：同一 agent 连续改同一文件。**

第一次 `edit_batch` 释放锁后，第二次立即获得。无等待。

## 死锁分析

**单文件不会死锁。** `edit_batch` 只锁一个文件，不会出现“A 持有 X 等 Y，B 持有 Y 等 X”。

**但如果将来跨文件事务：** 必须按路径字典序加锁，否则可能死锁。这是第二版跨文件事务的约束，第一版不涉及。

**锁泄漏：** 用 try-finally 保证释放。进程崩溃时锁自然消失（进程退出）。

## 与其他原语的关系

| 原语 | 关系 |
|---|---|
| `read_view` | 提供 `baseVersion`；不加锁，可能读到旧版，但版本戳标注 |
| `blast_radius` | 只读，不加锁；提供符号缓存失效通知 |
| `project_map` | 只读，不加锁 |
| `verify_test` | 只读执行（不碰源文件），不加锁 |

## 实现要点

- **锁结构**：`ConcurrentHashMap<String, Mutex>`，key 是规范化绝对路径
- **公平性**：`ReentrantLock(fair=true)` 或等效的 FIFO 队列
- **路径规范化**：Windows 的 `\` 和 `/` 统一，大小写敏感按平台
- **锁清理**：使用后保留在 map 中（避免频繁创建），或定期清理空闲锁
- **可配置超时**：通过 `edit_batch` 的 options 传入，缺省 30s
- **日志**：每次锁等待超过 1s 记录警告，便于诊断

## 验收标准

- [ ] 两个 `edit_batch` 基于同一版本改同一文件，第二个返回 `VERSION_MISMATCH`
- [ ] 两个 `edit_batch` 改不同文件，并行执行无阻塞
- [ ] 同一 agent 连续 `edit_batch` 同一文件，无等待
- [ ] 锁等待超时返回 `LOCK_TIMEOUT`，含 `waited_ms`
- [ ] 锁内校验版本，窗口期不存在
- [ ] 进程崩溃后锁不泄漏（重启后正常）
- [ ] 公平性：多个等待者按 FIFO 获取
- [ ] 路径规范化：`./engine.ts` 和 `engine.ts` 指向同一锁
- [ ] 协议 fixtures：`fixtures/edit_batch/lock_timeout.json`
- [ ] Java 端契约测试 + 客户端契约测试

## 验收证据要求

- [ ] 并发验证：10 个 agent 同时 edit_batch 同一文件，只有一个成功，其余 `VERSION_MISMATCH` 或 `LOCK_TIMEOUT`
- [ ] 并行验证：10 个 agent 同时 edit_batch 不同文件，全部成功，无等待
- [ ] 超时验证：一个 agent 持有锁 30s 以上（模拟），其他 agent 返回 `LOCK_TIMEOUT`
- [ ] 崩溃验证：持有锁时 kill 进程，重启后同一文件可正常写入
- [ ] 契约测试双向通过

## 约束

- **文件级锁**——不做模块级、项目级
- **进程内锁**——不做跨进程
- **单文件**——不做跨文件事务锁
- **读写不对称**——只锁写，读不加锁
- **不持久化**——锁在内存，进程退出即消失

---

## 需要你确认的两点

**① 锁超时的默认值。** 我定 30 秒。理由是 `edit_batch` 本身 < 100ms，30 秒意味着“异常情况”。如果你的工作流里有慢写入（比如大文件 + 复杂变更），可以调大。

**② 超时后模型的行为。** `LOCK_TIMEOUT` 返回后，模型可以选择：重试、先 `read_view` 拿最新版再重试、或放弃。这不需要工具干预，是模型的决策。但要确认：**是否需要工具在 `LOCK_TIMEOUT` 里自动附带最新版本？** 还是模型自己去 `read_view`？

我倾向**不自动附带**——模型拿到 `LOCK_TIMEOUT` 后，自己决定下一步。工具不替它做决策。但这可能多一次往返。

你确认这两点后，就可以交给 AI 实现。
